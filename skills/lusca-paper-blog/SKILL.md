# lusca-paper-blog — 论文博客化解读

**核心理念：把一篇论文"翻译"成开发者/技术从业者愿意点开、读得懂、读完觉得"这和我方向相关"的博客——不是缩写论文，而是讲一个戳中行业痛点、带点自问自答和打趣的故事。**

输入一篇论文的 `lusca-pdf-parse` 解析结果（默认）、`lusca-paper-read` 精读笔记、或论文地址本身，按"问题→思路→效果→与你何干"的叙事线，用**领域痛点**与**技术圈共鸣**拉近距离，再用**自问自答和轻度打趣**让它读起来像有人在跟你聊（生活类比只用于解释具体技术概念），产出 8-12 分钟可读完、标题活泼、段落短小、通俗但不丢要点的科普博客。立足**传播视角**：目标是让读者愿意点开、读完、记住一个 takeaway 并觉得"这能解我的问题"，而非复现论文或做学术评估。

## 与体系内其它 skill 的分工

| 场景 | 使用技能 |
|------|----------|
| 检索论文 | `lusca-paper-search` |
| PDF 解析为结构化 Markdown（忠实原文 + 图片抽取） | `lusca-pdf-parse` |
| 精读论文 / 批判性阅读笔记（给自己看） | `lusca-paper-read` |
| **把论文写成通俗科普博客（给同行读）** | **本技能（lusca-paper-blog）** |
| 论文润色（已有学术初稿） | `lusca-paper-polish` |
| 从精读笔记做会议海报 | `lusca-paper-poster` |

**在主链中的位置**：本技能消费 `lusca-pdf-parse` 的解析结果（默认）、`lusca-paper-read` 的精读笔记，或直接读论文地址。parse 负责"还原原文"、read 负责"读透"、blog 负责"讲好"——三种输入任选其一。

## 输入

博客化接受三种输入来源，从 `$ARGUMENTS` 与上下文自动识别：

- **`lusca-pdf-parse` 解析结果（默认）**：`outputs/lusca-pdf-parse/{slug}/parsed/*.md` + 同目录 `images/`。版面还原的忠实 Markdown（双栏重排、表格转写、公式保留、图已抽到本地），是博客事实层的首选来源——方法、公式、图表、结果数字都原样在册。图片复用 `parsed/images/`
- **`lusca-paper-read` 精读笔记**：`outputs/lusca-paper-read/{slug}/*.md` + `imgs/`。已提炼好研究问题/贡献/方法要点/关键结果/caveat，省去再读一遍；但**博客事实层以论文原文为准**（笔记含读者主观评估），笔记的批判性观点可参考进 caveat 节。图片复用 `imgs/`
- **论文地址（arXiv ID / URL / PDF 路径 / 粘贴文本）**：直接给论文链接时，skill 用 `WebFetch` 抓取全文（arXiv 优先 `arxiv.org/html/<id>`，无 HTML 版则下载 PDF 用 `Read` 分块读）再写博客。手头没有 parse/read 产出时走这条；复杂版面（双栏/公式/表格密集）先 `/lusca-pdf-parse` 解析更准，但直接给地址完全可行——它是和 parse/read 并列的一等输入

**默认**：未明确指定时按 parse 结果处理。**只追问一次**：完全找不到任何来源时，问一句位置后继续（这是唯一允许的追问）。

## 主流程

```
locate-source → read-or-reuse → outline-blog → write-blog → polish-tone → save
```

1. **定位来源**：解析 `$ARGUMENTS`——默认识别为 parse 结果；明确是 read 笔记则按笔记复用；是论文地址（arXiv/URL/PDF/文本）则 `WebFetch` 或 `Read` 读全文
2. **读/复用**：从来源提炼六样东西——研究问题（领域痛点）、核心贡献、方法要点（只讲思路与用途）、关键结果（1-3 个最亮数字）、主要 caveat、可用图片。**建立图片清单**：每张图标明「内容 → 归位节」，复用 parse/read 的图片直接拷贝到 `{slug}/imgs/`
3. **搭骨架**：`Read` `assets/blog-template.md`，对照博客结构模板规划各节；从模板的**标题范式**选一个活泼标题（论文关键词/简称 + 面向开发者的钩子）
4. **写博客**：按模板逐节写，遵循下方「核心准则」——通俗、深入浅出、行业共鸣、互动语气、篇幅、段落控制
5. **润色语气**：通读一遍——删学术腔、补自问自答与打趣（点缀别过密）、拆长段、检查标题与小标题是否干净、确认每段不超过 4-5 行
6. **落盘**：写到 `./outputs/lusca-paper-blog/{slug}/{YYYYMMDDHHmmss}_{slug}.md`，图片到 `{slug}/imgs/`；带 YAML frontmatter（见模板）；**文末出处块**三行（遵 CLAUDE.md）。落盘后跑 `python3 skills/lusca-paper-read/scripts/check_imgs.py outputs/lusca-paper-blog/{slug}/` 自检无孤儿图
7. **交付**：路径 + 标题 + 一句话定位；附后续衔接建议（见 §后续衔接）；**不内联重复展示完整博客**——已落盘，再贴一遍是冗余噪声

## 核心准则

### 通俗：把论文"翻译"成人话（但保留专业名词让人学到）

通俗不等于"把术语全换成大白话"——**专业名词要保留**，让读者读完既读懂论文又学到几个领域术语，只是首次出现时配一句白话：

- **保留专业名词 + 配白话**：术语首次出现用「术语（白话解释）」格式，如"GRPO（Group Relative Policy Optimization，一种强化学习算法）""TEDS（表格还原准确度，越接近 100 越好）"；解释要说清"它是什么、怎么读这个数"
- **评测指标要给判读方向**：报数字时附带"是什么量、越高/越低越好"，别让读者面对一串陌生缩写无从判断
- **公式只讲用途，不讲推导**：写"这个公式的任务是给每个词算一个重要性分数"，不写推导步骤；论文的核心公式最多给一个，且只用文字解释它"做什么"
- **绝不编造**：论文没说的不补；类比可以发挥，但论文事实（数字、方法、结论）必须忠于原文；读不清的标 `(uncertain)`

### 深入浅出：why → how → what

- 先讲**为什么这个问题重要**（读者的痛 / 场景），再讲**作者怎么想的**（思路，不是实现细节），最后讲**效果如何**（一个让人记住的对比）
- 复杂机制配**一个生活类比**：如把"长文档抽取截断"类比为"让你一口气抄完一整本电话簿，抄到一半手就酸了、后半本全凭印象编"
- **循序渐进**：每个概念先用一句话点透，再展开；不要一上来就堆术语

### 行业共鸣：戳开发者的领域痛点

读者是**开发者和技术从业者**——他们点进来是为了判断"这和我方向相关吗、能解决我的问题吗"。共鸣的主线是**领域痛点与技术圈共识**，不是日常生活：

- **导语用领域痛点或技术圈近期事件切入**：选目标读者大概率正在头疼/刚经历过的事（"做 RAG 的都被 PDF 表格解析丢数据坑过""刚发布的某大模型在长文档上翻车了"），把论文要解决的问题"演"成他们的切身体验，再引出论文
- **结合最近的技术新闻/产品发布/框架更新**：论文主题若关联近期热点（某模型上线、某基准刷榜、某趋势），可 `WebFetch` 查一条作开篇 hook，但只用于共鸣引子，**不用于改论文事实**
- **生活类比只用于解释具体技术概念**（如把注意力机制类比成"划重点"、把长文档截断类比成"抄电话簿抄到手酸"），**不作为共鸣主线**——开发者要的是"这正是我遇到的问题"，不是"这个比喻真巧妙"
- 痛点要**具体到方向/技术栈/场景**（"做 RAG 的人""调过 agent 的""踩过文档解析坑的"），越具体越能筛出目标读者

### 语气：可以自问自答，可以轻度打趣

博客不是论文，允许也更欢迎一点"有人在跟你聊"的语气——这是通俗博客区别于论文摘要的关键亲和力：

- **自问自答推进**：用"为什么会这样？因为……""那怎么办？"这类设问把读者带入下一个论点，比平铺直叙更抓人，尤其在抛出反直觉发现或转折时
- **轻度打趣拉近距离**：在破冰、段间过渡、点出反常识结果时用一句打趣（"对，就是你想的那个坑""听起来离谱，但数据就是这么写的"），让读者会心一下
- **自我互动的引子**：开头可以用一个设问或半开玩笑的吐槽把读者拉进来，再切入正题——"先问一个可能戳到你的问题……"比"本文提出……"好用得多
- **边界**：打趣服务于理解，不油滑、不抢事实；caveat、数字、方法原理这些地方保持清楚克制，不在严肃处抖机灵；通篇打趣密度别高，点缀即可，多了就腻

### 观点：要有自己的思考，别只当复读机

博客区别于论文摘要的另一点是**作者在场**——读者想看的是"一个懂行的人怎么看这篇论文"，不是论文摘要的转述：

- **给解读和判断**：在关键结果处给出自己的读法（"这个数字最值得在意的是……""我倾向于把它理解成……"），而不是只复述"论文报告了 X"
- **温和的质疑和推测**：对可疑之处可以提（"这里我有个怀疑""一种可能的解释是"），但标明是你的推测而非论文结论，稳妥的放到 caveat 节
- **换角度旁评**：偶尔跳出论文框架给一句（"换个角度看，这其实也说明……"），帮读者看到论文没明说的东西
- **边界**：自己的思考是基于事实的解读与判断，不是编造数据；论文没有的数字、引用、结论绝不补；推测要标明是推测

### 篇幅与节奏：8-12 分钟，段落短小

- **篇幅**：8-12 分钟阅读，中文约 400-550 字/分钟 → **目标 3500-6500 字**（含标题与空行）；宁可精炼不要注水
- **每段 ≤ 4-5 行**：长段拆成短段或列表；读者常在手机上读，大段文字会被跳过
- **多用小标题与列表**：降低视觉压力，但要保持叙事连贯，别碎成碎片

### 结构：分点用列表，段间要连贯

并列内容要让人扫得动、全文要让人读得顺，结构上做到两件事：

- **并列分点用 markdown 列表，不要塞在一段**：凡是用"第一/第二""一是/二是""首先/其次/最后"或顿号罗列的并列要点，一律拆成无序列表逐行写；只有 2 个且语义紧密连贯的并列可留在段里，3 个及以上必须列表化
- **列表不要孤立**：列表前一句要"引出"（"我建议你关注三点""几个该打问号的地方"），列表后要有一句收束或过渡到下一段，别让列表突兀地夹在段落之间
- **段间要有承接**：每段开头尽量接住上一段尾巴（"那……""换句话说""但这还不够""落到实操""再往远看"），让全文读起来是一条线，不是一堆散点
- **一句话总结放开头作 TL;DR**：放氛围图后、导语前，用引用块给核心结论（用什么方法解决什么问题、对谁有用），让读者一眼抓核心、判断要不要读下去；结尾不再重复

宁可把多个机制/理由/条件拆成列表，也不要压成"一段塞五点"——后者读者会跳读，而且显得零散。

### 标题：活泼 + 论文关键词 + 面向开发者的钩子

- **用论文的易识别关键词**——简称、缩写或核心概念（如 ExtractBench、Mamba、CRISPR-Kids），**不塞完整冗长标题**；完整标题留给 frontmatter `paper` 字段与正文自然提及
- **加一个面向开发者的钩子**：戳领域痛点的提问 / 数字反差 / 技术受益点，任选其一，别堆；钩子要让人感到"这可能和我有关"
- **小标题（H2）干净直白**：用"它的思路是什么？""效果到底怎么样？"这样的直白问句，**不带"（不钻细节）""（小段 caveat）"这类指导性括注**——那是模板里的写法提示，不是成文标题
- 范式与范例见 `assets/blog-template.md` 的「标题范式」节——**写标题前必读**

### 图片与视觉：外部氛围图一张 + 论文原图该嵌就嵌

两类图分工，"一张"只约束外部氛围图，不约束论文原图：

- **外部氛围图只要一张（开头）**：**跑 `scripts/fetch_cover.py` 获取**（禁止手选——手选会反复取同一张），放 H1 后正文最开头，**无下方 caption**。脚本合并 Bing 每日一图池（≈ 15 张）与 picsum.photos 全量池（≈ 300 张）为候选，用持久化登记文件（`~/.cache/lusca-skill/lusca-paper-blog/used_covers.json`，跨项目跨会话）记录已用过的图，**每次只从没用过的里选**——两池全用完才清空登记重新循环，保证跨文章长期不重复；离线取不到时退化为带唯一 seed 的 picsum 直链。正文直接用脚本返回的外链 URL，脚本同时下载备份到 `imgs/cover.jpg`。全篇只这一张外部图，不再多处点缀
- **论文原图该嵌就嵌（不限张数）**：结果图、架构图、pipeline 图等承载事实的论文图，转存到 `imgs/` 嵌入正文，**配一句白话 caption**（解释图说明什么、读者该看什么），**严禁只写文字路径**——这是事实层，和氛围图不是一回事，别因为"一张图"就删掉
- **封面图获取脚本用法（必跑）**：
  ```bash
  python3 skills/lusca-paper-blog/scripts/fetch_cover.py <slug> <YYYYMMDDHHmmss> outputs/lusca-paper-blog/<slug>/
  ```
  输出 JSON `{"url": "...", "backup": "imgs/cover.jpg", "source": "..."}` → `url` 用于正文 `![氛围图](url)` + frontmatter `cover`（必须 http 开头）；`backup` → frontmatter `cover_backup`；`source` → frontmatter `cover_source`
- **emoji 适当点缀，不堆砌**：资源块每条配平台 emoji（📄 论文 / 💻 代码 / 🧩 模型 / 📊 数据集 / 🎮 Demo）；正文也适当加——H2 小标题配一个语义 emoji（如 🎯🛠️📈🤔🧊💡）、列表关键词配相关 emoji（如 🎓 学、🔁 迭代、📋 表格、➗ 公式）；约束：数字/基准结果/caveat 严肃处不加、语义相关不重复、不每句都加

### 项目资源块：前面就给链接，方便动手

开发者点进来常带着"能不能去试"的问题，别让他们翻到结尾才找到链接：

- **在导语后、正文第一节前，放一个资源链接块**：论文（arXiv/PDF）、代码仓库、数据集、项目主页/demo，用引用块、**每条一行**、**markdown 链接 `[显示文字](URL)`**；显示文字用平台/资源名（如 `GitHub · org/repo`、`arXiv <id>`、`HuggingFace · <name>`），别堆在一行、别裸贴长 URL
- 链接从论文 frontmatter / abstract / footnote / 附录搜集；**没有的不编、不留"待补充"占位**，有几个列几个
- 用博客语气的提示语领起（"想自己动手？""资源在这"），比干巴巴的"相关链接"更搭调

  ```
  outputs/lusca-paper-blog/{slug}/
    ├── {YYYYMMDDHHmmss}_{slug}.md   # 博客文章

  ```
- **slug**：取自论文标题或 arXiv ID（kebab-case）；若基于 parse/read 产出，与上游同 slug 以便对照
- **frontmatter**：`title`（博客标题，活泼版，用关键词不塞全名）/ `subtitle`（可选）/ `paper`（原论文完整标题）/ `authors` / `arxiv` / `blog_date` / `read_minutes` / `slug` / `category`（单一主分类）/ `tags`（2-4 个泛化技术标签）/ `abstract`（≤200 字博文摘要）/ `cover`（氛围图外链 URL）/ `cover_backup`（本地备份路径）/ `cover_source`（可选，来源描述）——见模板
- **`category` 与 `tags` 用泛化技术标签，不造论文专属细标签**（如 ExtractBench、某模型代号只进标题与正文，不进 tags）：
  - **`category`（单选，技术大类）**：人工智能 / 大模型（LLM） / 机器学习 / 深度学习 / NLP / 计算机视觉 / 多模态 / 强化学习 / RAG / Agent / 智能文档 / 知识图谱
  - **`tags`（多选 2-4 个，泛化）**：LLM / AIGC / 人工智能 / 机器学习 / 深度学习 / NLP / 计算机视觉 / 多模态 / 强化学习 / RAG / Agent / 智能文档 / 知识图谱 / 大模型应用 / AI 评测
- **`cover` 必须是 http(s):// 开头的图片直链**——正文实际能加载的远程图片地址，❌ 严禁填 `Bing 每日一图 · <copyright>` 这类文字描述（文字来源描述放 `cover_source`）；落盘前自检 `cover` 以 `http` 开头，否则不合规
- **`abstract` 是 frontmatter 的博文摘要**（≤200 字中文）：用于平台描述/SEO/列表预览，概括"论文讲了什么、核心贡献、对读者意味什么"；与正文 TL;DR（一句话钩子）互补——abstract 是完整段落、TL;DR 是一句话
- **文末出处块**（遵 CLAUDE.md「文档输出规范」，三行）：
  ```
  > 作者：lusca
  > 版本：lusca-paper-blog v1.7.1
  > 出处：https://github.com/yjmm10/lusca-skill/tree/main/skills/lusca-paper-blog
  ```
- **段落不硬换行**：遵 CLAUDE.md——正文段落与列表项在源码里写在一行，段间空行分隔，不在句中按列宽折行
