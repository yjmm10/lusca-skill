# lusca-news-report — 新闻/事件深度调研与完整报告

**核心理念：调研一个事件的价值在于把来龙去脉、各方立场、可信证据一并摆清——但前提是这个事件真实存在、且找对了那件事。在模糊信息上盖一份详尽报告，比不写更糟。**

输入用户描述的事件/主题/关键词/链接，先**核验新闻真实存在并消歧**（不实或无法定位就停下来与用户确认），再**多平台采集反馈**（官方宣传与答复、权威媒体、社交平台与用户评价），整合成带**时间线 + 模块化分析**的完整事件报告；完整报告偏官方，如需发布可**追加通俗博文版**。立足**读者视角**：让没追过这件事的人读完即懂"发生了什么、各方怎么看、可信度如何"，而非堆砌链接或站队。

## 输入

从 `$ARGUMENTS` 与上下文自动解析事件描述（事件名 / 主体 / 关键词 / 链接 / 时间线索）。**本技能设两道确认门**（见 §核验护栏）——这是它与文献检索类 skill 的关键差异，**不是啰嗦**：学术论文有稳定标识（arXiv ID / DOI），而新闻事件模糊、时效、同名实体多，盖着一份详尽报告后才发现"查错事件"或"追了个谣言"，会浪费整轮多平台采集、还会误导读者。所以信息不足或无法定位时，**先停下来问一句**，比闷头写完更负责。

## 主流程

```
intake → 核验(确认门) → 多平台采集 → 整合分析 → 完整报告 → (可选)博文版 → save
```

1. **intake**：解析事件描述，提炼检索关键词（中英、主体名、时间窗）。完全无信息时追问一次（唯一非确认门的追问）
2. **核验（确认门，见 §核验护栏）**：用 WebSearch 确认新闻真实存在、定位是哪一件事、查辟谣状态
3. **多平台采集**：`Read` `references/platforms.md`，按"官方 / 权威媒体 / 社交平台 / 用户评价 / 垂直专业"五类渠道检索，采集宣传方式、用户评价、官方答复
4. **整合分析**：模块化拆解（背景 / 事实 / 时间线 / 各方反应 / 影响 / 争议 / 信息缺口），时间线用 mermaid 或表格
5. **完整报告**：`Read` `assets/report-template.md`，严格对照模板逐节填写，落盘
6. **（可选）博文版**：用户要求"出个博文版 / 公众号版 / 通俗版"时，`Read` `assets/blog-post-template.md`，基于完整报告改写成通俗可发布的博文
7. **save**：报告落盘到 `./outputs/lusca-news-report/{slug}/{YYYYMMDDHHmmss}_{slug}.md`（博文版同目录加 `_blog` 后缀）；交付路径 + 一两句要点 + 后续衔接；**不内联重复展示完整报告**

## 核验护栏（核心）

新闻调研最容易在源头翻车：调研了根本不存在的事、调研了同名事件里的错的一件、把营销号炒作当成真新闻深挖。故设两道确认门——**信息不足就停、歧义就问、疑似谣言就标记**。

**门 1 · 真实存在 + 可定位**：首轮 WebSearch 后，若**无任何权威 / 一手报道**命中（只有自媒体互抄、无首发来源、无时间地点），**停下**告知用户"未检索到该事件的可靠报道"，请其补全（时间 / 人物 / 出处链接 / 关键词），不要在空气上盖报告。

**门 2 · 消歧**：若命中**多个可能匹配的事件**（同名、同主体不同时间、同主题不同事件），**停下**列出候选（每条一行：事件 + 时间 + 一句区分），请用户确认是哪一件后再继续。

**疑似谣言标记**：若事件仅见于营销号 / 匿名消息、或已有权威辟谣，**不当作已证实事实深挖**——明确标注"该消息目前未经验证 / 已被辟谣"，与用户确认是按"未经证实"继续，还是中止。

> 通过两道门后，后续采集与分析**不再逐条追问**；遇到单条信源冲突，在报告里如实并列并标可信度即可。

---

## 多平台采集（核心）

**为何要全平台**：单一信源只给一个切面。官方只说想说的、媒体各有立场、用户评价藏在评论区。把五类渠道都扫一遍，才能让读者看到事件全貌而非某一方的话术。详见 `references/platforms.md`（每类渠道的检索词构造、典型入口、注意事项 + 信源可信度分级表）。

| 渠道 | 采集什么 | 典型入口 |
|------|---------|---------|
| 官方 | 宣传方式、口径、声明、致歉、答复 | 官网 / 公告、官方微博 / 公众号、X/Twitter、发布会实录 |
| 权威媒体 | 事实层核实、关键时间点、数据 | 主流新闻媒体报道 |
| 社交平台/社区 | 舆论倾向、用户评价、争议焦点 | 微博、知乎、Reddit、X、B站、小红书、抖音、V2EX、HN |
| 用户评价 | 真实使用者反馈、投诉、评分 | 应用商店、黑猫投诉、电商评价 |
| 垂直专业 | 行业视角、KOL / 分析师判断 | 行业媒体、专业评测、领域 KOL |

采集要点：

- **官方宣传 vs 事实**：分开记。官方"怎么说"是宣传口径，"实际发生了什么"以一手 / 权威为准——二者冲突时在报告里并列并标可信度
- **用户评价要带分布**：不只挑最赞 / 最骂，给"正 / 中 / 负"的分布与代表性观点，避免以偏概全
- **官方答复要溯源**：引用官方声明尽量给可点击出处（公告链接 / 微博链接 / 截图说明），让读者可追溯
- **平台覆盖按事件相关性裁剪**：技术事件重 HN / Reddit / V2EX / 知乎；消费事件重 小红书 / 电商 / 应用商店；政策事件重 权威媒体 / 官方——不必每件事都扫全平台，但要在报告里说明"扫了哪些、没扫哪些、为什么"

## 完整报告（核心准则）

### 严谨：事实层绝不编造，区分事实与评估

- **基于已核实信源**：每个关键事实尽量指向一手或权威来源；读不清、未证实的标 `(uncertain)` 或"未经证实"，绝不补全
- **区分事实与评估**：第 1–4 节（核验 / 背景 / 时间线 / 各方反应）是客观陈述；分析性判断用"评估："前缀或明确语气区分，不混入事实陈述
- **信源可信度分级**：报告"信息来源索引"按 一手（官方 / 当事人 / 权威通报）> 主流权威媒体 > 行业垂直媒体 > 社交大V / KOL > 普通用户评论 > 营销号 / 匿名消息 分级，让读者自行权衡
- **辟谣 / 营销号识别**：仅见于营销号、或已被权威辟谣的内容，不当作已证实事实写入；疑似谣言单独标注

### 模块化分析

报告按模块逐项分析（对照 `assets/report-template.md`）：背景与核心事实（5W1H）、时间线、各方反应（官方 / 媒体 / 用户 / KOL 分节）、影响与受众、争议与风险、信息缺口。每个模块都要"分析"而非"罗列"——给出该模块说明了什么、可信度如何、有无信息缺口。

### 时间线

事件有发展过程的，用 mermaid `flowchart TD` 或表格画时间线，节点为"时间 + 关键节点"，按时间自上而下；图下附几句解读（起点 → 转折 → 当前状态）。一次性事件无时间线的，省略并说明。

### 段落与结构

遵 CLAUDE.md「文档输出规范」：正文段落与列表项在源码里**写在一行**（不在句中按列宽折行），段间空行分隔；并列分点（≥3 个）用 markdown 列表，不塞在一段；mermaid 节点 ID 语义化、解读用内容不用字母 ID（遵 `lusca-paper-read` 约定）。

## 博文版（可选）

完整报告偏官方、信息密度高，适合存档与决策；若要**发布给大众读**（公众号 / 博客 / 社区），追加一份博文版：基于完整报告的事实层，用通俗、有共鸣、带互动的语气重讲一遍事件——不是缩写报告，而是讲一个让普通读者愿意点开、读完、有 takeaway 的故事。

- **触发**：用户要求"出个博文版 / 公众号版 / 通俗版 / 发出去的版本"时才写；默认只出完整报告
- **保留事实层、换表达层**：博文版的事实必须与完整报告一致（不因通俗而编造或夸大），只换语气与结构；不确定沿用 `(uncertain)`
- **对照 `assets/blog-post-template.md`**：氛围图 + 一句话带走 + 戳共鸣导语 + 白话讲事件 + 各方怎么看（轻量）+ 简化时间线 + 我怎么看 + 冷静一下；tone 参考 `lusca-paper-blog` 的通俗 / 互动 / 作者在场（但内容对象是事件不是论文）

## 输出与存放

- **目录结构**（每个事件一个文件夹）：
  ```
  outputs/lusca-news-report/{slug}/
    ├── {YYYYMMDDHHmmss}_{slug}.md          # 完整事件报告
    ├── {YYYYMMDDHHmmss}_{slug}_blog.md     # 博文版（可选）
    └── imgs/                                # 关键截图（官方公告 / 数据图等，可选）
  ```
- **slug**：取自事件简称（kebab-case）
- **frontmatter**：`title` / `event`（事件全称）/ `subject`（主题标签）/ `time_range` / `platforms`（扫过的渠道）/ `generated_at` / `generator`（本技能名与版本）/ `uncertain_count`（uncertain 条目数）
- **文末出处块**（遵 CLAUDE.md「文档输出规范」，三行）：
  ```
  > 作者：lusca
  > 版本：lusca-news-report v<version>
  > 出处：https://github.com/yjmm10/lusca-skill/tree/main/skills/lusca-news-report
  ```
- **交付精简**：落盘后只返回路径 + 一两句要点（事件定位 + 最关键发现 / 不确定），**不内联重复展示完整报告**——完整内容已落盘，再贴一遍是冗余噪声

## 后续衔接

完整报告落盘后——按常用度排序：

- **（若未出）博文版**：报告太官方、要发布给大众时，基于报告追加通俗博文版（公众号 / 博客可发）
- **`/lusca`**：复盘本次调研中 skill 暴露的问题（核验判断、平台覆盖、信源分级、模块分析质量）
- **`/lusca-paper-search`**：若事件涉及学术 / 技术论文，可顺带检索相关论文佐证（如某 AI 产品的技术报告）

> 话术示例：报告路径 + 要点后补一句「要发公众号的话，我可以基于这份报告再出个通俗博文版；觉得这次调研哪里不到位，可用 `/lusca` 复盘」。

## 版本管理

**当前版本**：见 frontmatter `version` 与 `CHANGELOG.md` 最新条目。

每次修改本技能**必须**：

1. 递增 `SKILL.md` frontmatter `version`
2. 写入 `CHANGELOG.md`（Added / Changed / Fixed / Removed）
3. 向用户说明版本号与变更要点
4. 本 skill 源目录或 frontmatter 有增删 / 重命名时，按工作区规范跑 `./scripts/link-project.sh` 同步发现层
