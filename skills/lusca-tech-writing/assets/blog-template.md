# blog-template — 成文骨架与落盘规范

写大纲前与落盘前各读一遍。语气规范与 `lusca-paper-blog` 一致（自问自答、轻度打趣点缀、段落
短小），此处只列要点；本模板重点是**新手向叙事线**与**多源成文的落盘格式**。

## 一、标题范式

主题关键词 + 新手钩子，任选其一，不堆：

1. **一文搞懂**：`一文搞懂 X：从概念到跑通第一个示例`
2. **入门承诺**：`X 入门：从 0 到 5 分钟跑通`
3. **戳痛点提问**：`X 到底是什么？为什么大家都在聊`
4. **完整教程**：`X 上手指南：原理 + 快速上手 + 常见坑`
5. **散料整合**：`关于 X 的零散资料，这篇帮你串起来`

小标题（H2）干净直白，可用问句（"X 到底解决了什么问题？"），**不带**指导性括注。

## 二、章节骨架（新手向叙事线）

按主题取舍，H2 数量 5–8 个为宜；「模块快速上手」仅模块化主题需要（见
`references/code-and-quickstart.md`）。

| 节 | 内容 | 字数（中文字符，不含代码） |
|----|------|------|
| H1 + 封面图 | fetch_cover.py 取图，无 caption | — |
| TL;DR | 引用块 1–2 句：这是什么、读完你能带走什么 | 60–120 |
| 导语 | **两三句内切入痛点**（文档散 / 教程过时 / 不知从哪下手），立刻引出主题；不铺陈、不复述读者已知的事 | 100–180 |
| 资源块 | 引用块，每条一行：官方文档 / 仓库 / demo，`[名称](URL)` 格式 | 3–6 条 |
| X 是什么 | 概念 + 一个生活类比 + 术语首现配白话；不写教科书式定义堆叠 | 300–500 |
| 能用来做什么 / 为什么值得学 | 真实场景，戳目标读者的具体痛点 | 250–400 |
| 原理 / 核心机制 | 讲思路不讲推导，配架构 / 流程图；配一张图 | 400–800 |
| 5 分钟跑起来 | 安装 → 最小示例 → 跑通标志 | 300–500 + 代码 |
| 各模块快速上手 | 每模块：干什么 + 最小代码 + 验证跑通（+ 第一个坑） | 每模块 150–300 + 代码 |
| 对比 / 选型（可选） | 与同类工具对照，给"什么场景选它"的判断 | 250–400 |
| 常见坑与 FAQ | 列表化，每条：坑 + 一句解法 | 300–500 |
| 进阶与拓展（推荐） | 调优参数 / 生态工具 / 组合用法 / 边界局限，写法见 §五 | 300–600 |
| 结尾收束 | 不设"总结"标签，承接上文过渡 + 下一步深入方向 | 100–200 |
| 参考来源 | 全部核心参考 + 补充，见 §四 | — |

总量 3500–6500 字（8–12 分钟阅读）；每段 ≤4–5 行；并列 3 项以上用列表不塞段。**冗余挤出去
的空间让给干货与拓展，而不是让给更多铺垫。**

## 三、frontmatter

```yaml
---
title: 博客标题（活泼版）
subtitle: 可选副题
topic: 用户输入的主题原文
slug: kebab-case-slug
category: 单一主分类（技术大类，如 人工智能 / 后端 / 前端 / 数据库 / DevTools）
tags: [2-4 个泛化技术标签]
abstract: ≤200 字摘要，供平台列表预览
read_minutes: 9
blog_date: YYYY-MM-DD
cover: https://...        # fetch_cover.py 返回的 url，必须 http 开头
cover_backup: imgs/cover.jpg
cover_source: Bing 每日一图 · ...   # 文字来源描述放这里
sources:                  # 全部核心参考，与文末参考来源一致
  - title: 官方文档标题
    url: https://...
generator: lusca-tech-writing v1.0.0
generated_at: YYYY-MM-DD HH:mm
---
```

自检：`cover` 以 `http` 开头；`sources` 数量 ≥3；`abstract` ≤200 字。

## 四、图注与参考来源格式

图注（每图必有，严禁只写路径）：

```markdown
![XX 架构示意](imgs/01-arch.png)

> 图：XX 的整体架构，数据自上而下流经三个模块（图源：[官方文档 · Architecture](URL)）
```

参考来源（文末，正文零来源噪音的正当出口）：

```markdown
## 参考来源

- [官方文档 · Getting Started](https://...) — 概念定义与安装步骤的主要参考
- [博客 · X 实战笔记](https://...) — 模块用法示例与踩坑清单参考
```

每条附一句**贡献了什么**，帮读者按需深入；补充参考（只贡献个别事实的）列在核心参考之后。

## 五、干货密度与拓展（写完每节都过一遍）

新手向 ≠ 话多。恰恰相反——新手最缺的是**能带走的具体东西**，不是环绕音效式的讲解。冗余
挤掉的篇幅让给干货与拓展。

### 反冗余、反课程腔

- **禁教学套话**："在本节中，我们将学习……""接下来让我们了解一下……""首先恭喜你完成
  安装"——一律不写，直接进入内容
- **禁大纲复述**：开头不要"本文将分 X 个部分介绍……"——TL;DR + 小标题已经承担了导航
- **禁空过渡**："说到这里，我们再来看看……"这类不承载信息的句子删掉；段间承接用半句
  （"那实操呢？"）不用整句客套
- **一句一信息**：写完每节回读一遍，凡是不删就影响理解的句子都删；删完不影响理解的，当时
  就不该写
- **空评价换事实**："非常强大 / 十分方便 / 性能优异"→ 具体到"官方基准 X 场景比 Y 快 30%
  （版本 v2.1，见参考[2]）"；没有数字支撑的评价不写

### 干货化改写对照

**反例（空话）**：Docker 的网络功能非常强大，支持多种网络模式，可以满足各种场景的需求。

**正例（干货）**：Docker 默认用 bridge 模式：容器走 docker0 网桥 NAT 出网，外部访问要 `-p
8080:80` 映射端口。容器间互相访问用容器名（需自定义网络，默认 bridge 不带 DNS）。跨主机
才考虑 overlay——单机场景不要上。

### 拓展维度（至少覆盖 2–3 个）

基础讲清后，在「进阶与拓展」节或相关小节末尾给进阶一层，维度任选：

- **调优**：关键参数与默认值取舍（"生产环境把 X 调到多少、为什么"）
- **生态**：周边工具 / 插件 / 替代实现，各一句话定位
- **组合用法**：与读者已有技术栈怎么接（"已用 K8s 的团队配 operator"）
- **边界与局限**：它不擅长什么、什么时候该换方案——比优点更省读者时间
- **深入路径**：想再往深走该读什么（源码模块 / RFC / 官方 advanced 文档）

拓展素材来自调研阶段的知识地图「进阶拓展」块（检索角度加 `X best practices` /
`X advanced tips` / `X performance tuning`）；同样反拼凑、同样要消化成一条叙事。拓展不等于
注水：每条拓展也要具体可带走（一个参数名、一个工具名、一条边界判断），罗列关键词不算拓展。

## 六、语气与格式要点（对照 lusca-paper-blog，只列清单）

- 自问自答推进（"为什么会这样？因为……"）；轻度打趣点缀不过密
- 术语首现「术语（白话解释）」；机制配一个生活类比
- 段间承接："那……""落到实操""但这还不够"
- emoji：H2 配一个语义 emoji，列表关键词可配；数字 / caveat 严肃处不加
- **一段一行**：段落与列表项在源码里写在一行，段间空行，绝不句中折行
- 不带文末出处块（作者 / 版本 / 生成信息只进 frontmatter `generator`）
