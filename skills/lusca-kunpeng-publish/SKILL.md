# lusca-kunpeng-publish — 鲲鹏社区发表合规审计与改进

输入一篇（或一组）技术稿件 → 对照鲲鹏社区发表要求做六维审计 → 产出审查报告与改进稿件。头号下线原因是 AI 痕迹，而 AI 痕迹的正解是**真实化**：实机验证、真实数据、人工重写——不是伪装。

## 红线原则

- **不做检测规避**：不帮用户"降低 AI 检测率""绕过平台审核"；只做让内容真实可信、可署名发布的改进。用户问"怎么过 AI 检测"，如实答：唯一正当路径是实机验证 + 自己的数据/截图 + 亲口重写
- **事实不动手脚**：绝不编造实测数据、运行结果、版本号；未验证的技术断言标 `(uncertain)` 并列入人工待办
- **改动可追溯**：改稿保留原意与信息结构；参考来源只增不删；技术性修正（错误命令、错误 API）必须逐条报告
- **规范以官方为准**：鲲鹏社区《内容发布规范》页面（见 `references/publish-requirements.md`）为 JS 渲染，AI 抓不到正文——每次审计前提醒用户人工核对最新口径，本 skill 的要求汇总只作基线

## 主流程

1. **读稿定位**：输入是什么（单篇 / 系列）、什么体裁（教程 / 实践 / 案例 / 征文）、目标栏目（社区博客 / 案例专区 / 活动）；稿件来源（AI 生成 / 人写 / 混合）如实问清或按证据推断
2. **六维审计**（→ `references/audit-checklist.md`）：外部链接（要求：零外链）、图片（要求：零图）、表述专业严谨、实操完整性（代码+命令+步骤）、实际应用、AI 痕迹与原创——前五维对应鲲鹏发布要求五条，第六维是生态下线红线
3. **审查报告**：问题清单表（维度 / 位置 / 问题 / 严重度 / 处理方），按「AI 可改 / 必须人工」分栏
4. **执行 AI 可改项**（→ `references/revision-playbook.md`）：措辞去模板腔、标题摘要标签、结构层次、鲲鹏关联强化、代码技术性修复；**改稿写回前把"必须人工"清单摊给用户确认**
5. **交付**：审查报告 + 改稿 + 人工待办清单（实机验证、真实截图、署名重写段）

## 产出与落盘

- 审查报告：`<原目录>/<原文件名>.audit.md`（单篇）或汇总一份（系列）
- 改稿：默认**原地写回**（与 tech-writing 系列操作一致）；用户要求保留原稿时写 `<原文件名>.revised.md`
- 人工待办清单并入审查报告末节，逐条可勾选
