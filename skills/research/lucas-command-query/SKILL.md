# lucas-command-query — 需求调研与可行性

**核心理念：调研的价值不在信息量，而在把「想做什么」翻译成「别人做到哪了、我们该怎么做」。理解错了，后面查得越全越亏。**

## 主流程

```
理解确认 → 调研（产品 / 开源 / 论文）→ 需求整理（带依据）→ 意见与可行性方案 → 落盘
```

### 1. 理解确认

先用两三句复述你理解的需求：

```
我认为你要做的是：<做什么>，给 <谁>，解决 <什么问题>。
关键假设：<可能影响调研方向的 1-3 条>。
```

- 有**影响方向**的歧义（目标是什么、面向谁、必须私有化吗、有无硬约束）→ 一次问完，每题给候选答案
- 没歧义或用户说“别问了先查” → 直接调研，把假设写进报告
- 不要问调研本身能回答的问题（“市面上有竞品吗”就是任务本身）

### 2. 调研三条线

| 线 | 查什么 | 关键判据 |
|----|--------|---------|
| 市面产品 | 谁在做、功能、定价/模式、用户评价与抱怨、演进方向 | 定位差异、价格带、**用户不满在哪**（差异化的入口） |
| 开源项目 | GitHub / PyPI / HuggingFace 上的现成轮子 | 最近提交、release 节奏、issue 响应、维护者、许可证、改造成本 |
| 论文（按需） | 技术类需求才查 arXiv / Google Scholar；只看方法与工程可达性 | 数据/算力门槛、SOTA 与真实链路的差距、有无代码 |

要点：

- **中英各查一轮**，加时间限定（近 1-2 年）
- **star 数是弱信号**：18 个月没提交要明确写「疑似停更」；许可证影响能否商用，必须写
- **数字必须可溯源**（star、价格、性能都标采集日期），查不到写 `(uncertain)`，不凭印象填
- 技术类需求可复用 `skills/lucas-paper-search/scripts/search_papers.py` 做论文检索；不可用时用 WebSearch
- **查不全就说查不全**，写进信息缺口

### 3. 需求整理

按层拆，条目要能验收：

- **目标**：为什么做、什么算做成
- **用户与场景**：谁用、什么时候用、现在怎么凑合
- **功能需求**：逐条 `R1..Rn`，动词开头、可验收（不写“效果好”）
- **约束**：预算、人力、时间、技术栈、部署形态、合规
- **不做什么**：本版边界

每条需求后面挂调研依据，并区分证据强度：

```
R1 批量导入 —— 竞品 A/B 都有，用户抱怨集中在手动逐条（产品 A 差评、issue #12）  [有依据]
R2 本地化部署 —— 客户合规要求；开源项目 C 可改造                                [推测]
R3 延迟 <200ms —— 论文 D 报告 180ms，未含预处理，需实测                          [待验证]
```

### 4. 意见与可行性方案

- **结论先行**：做 / 有条件做 / 不做或换角度，一句话理由
- **方案对比**（至少两个，必须包含“不自己造”）：直接采购、基于开源改造、自研最小核心、换角度缩小范围；按能力覆盖、成本、上线时间、维护、锁定风险、合规来比
- **推荐路线**：分步走，第一步是**能验证可行性的最小动作**（访谈、原型、拿开源跑通），不是先建大工程
- **主要风险**：每条风险配一个一两周内能做完、判据可证伪的验证动作
- **不做什么**：防止范围膨胀

### 5. 落盘

写到 `./outputs/lucas-command-query/{slug}/{YYYYMMDDHHmmss}_{slug}.md`，frontmatter 含 `title` / `topic` / `generated_at` / `generator` / `uncertain_count`。

报告结构固定为：需求理解 → 调研发现（产品 / 开源 / 论文）→ 需求整理（带依据）→ 意见与可行性方案 → 信息缺口 → 来源。

交付时只给路径 + 结论要点 + 最需要先验证的一点，不内联重复全文。

## 交付要求

- 结论先行，别只给一张竞品功能表
- 区分事实与判断，未核实的标 `uncertain`
- 段落和列表项在源码里一行写完，不按列宽折行
- 交付末尾附一句后续衔接：需要深读论文用 `/lucas-pdf-parse` + `/lucas-paper-read`；要对外发布用 `/lucas-report-blog`
