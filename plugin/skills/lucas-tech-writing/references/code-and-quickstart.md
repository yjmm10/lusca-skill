# code-and-quickstart — 代码补全与快速上手模块

新手读技术文章的目的是**动手**。代码块是动手的抓手：缺代码、代码跑不通、API 是编的，文章
价值直接归零。本规范两条主线：**缺代码必须补，补的必须真**。

## 一、代码从哪来（优先级）

1. **源文档自带的代码**：优先消化采用。注意两点——
   - 与成文采用的版本对齐：源文档代码基于旧版本的，按官方 changelog / 最新文档调整后再用
   - 调整过的代码要自洽：import、初始化、调用链在成文内部能对上
2. **官方仓库的 README / examples / quickstart**：源文档缺代码时，fetch 官方仓库补
3. **官方文档的代码片段**：API 用法以官方文档为准
4. **自己组织编写**：以上来源只有片段、需要拼装成完整可跑示例时，基于查证过的 API 自己写

**禁止**：凭印象写 API、写"示意性伪代码"冒充可运行、用 `...` 省略关键步骤。

## 二、API 查证（写进文章前必做）

对成文中出现的**每一个**关键 API 调用（函数名、类名、参数、import 路径）：

- 能对应到官方文档 / 仓库源码的具体位置（fetch 确认，不是"我记得有这个函数"）
- 参数名、默认值、import 路径与该版本一致
- **查证失败的 API 不写**：换用查证过的等价写法，或改为文字描述并标 uncertain

依赖与版本随代码标明：

````markdown
```bash
pip install somepkg>=2.0
```
````

代码块内用注释标注版本敏感处（如 `# v2.x API；v1 用 xxx()`）。

## 三、可运行底线

一段代码能进文章，必须同时满足：

- import 齐全、依赖明确（含安装命令与版本）
- 语法完整，从上到下复制粘贴能跑通最小路径
- 输出可预期：能说出"跑通后你应该看到什么"
- 长度克制：单块 ≤25 行为宜；更长的拆步骤分块，每块配一句"这一步在做什么"

## 四、快速上手模块（模块化主题必有）

主题是**多模块框架 / 工具库 / 平台**时（如"包含 CLI、SDK、Server 三部分"），文章必须有
快速上手部分，结构固定：

1. **5 分钟最小示例**（整体跑通）：安装 → 最短路径代码 → 一句"跑通标志"
   （"终端输出 `xxx` 即成功"）
2. **逐模块 quick start**，每个核心模块一节（3–6 个为宜），每节三件套：
   - **这模块解决什么**：一句话，接在主题叙事线上（不是干巴巴的功能罗列）
   - **最小代码**：≤15–20 行，可独立跑，与本模块强相关
   - **怎么验证跑通**：预期输出 / 现象一句话；该模块的"第一个坑"如有则附一句

写法示例（示意，非真实 API）：

> **Fetch 模块**：负责把网页拉成本地文本，是整条流水线的入口。
>
> ```python
> from somepkg.fetch import Crawler
> c = Crawler(polite_delay=1.0)
> page = c.get("https://example.com")
> print(page.text[:200])
> ```
>
> 打印出网页正文开头即跑通。第一个坑：不加 `polite_delay` 会被目标站限流。

非模块化主题（单一概念 / 协议 / 算法）不设逐模块节，快速上手并入「安装与最小示例」节，
写清：装好 → 跑通 → 验证标志。

## 五、代码与反拼凑的关系

- 代码同样要**消化**：不同来源的代码片段风格不一（命名、语言、版本），采用前统一成一种风格、
  一个版本口径，**不允许上文 Python 下文突然切到没交代语境的另一种写法**
- 补查来的代码与源文档的代码**融为一体**：读者看不出哪段来自哪篇文档——参考来源节统一致谢
- 命令行示例标注运行语境（bash 块 + 需要的 cwd / 前置条件），Windows / macOS 差异大时各给一条
