# anti-patchwork — 反拼凑准则与自检

**拼凑**是本 skill 的头号失败模式：一篇文档贡献一个章节、一段摘一个来源，读者一眼看出
"这是从好几篇文章粘来的"。本 skill 的承诺是反着来的——**像一位作者自己研究后独立写出的
一篇文章**。来源是调研素材，成文里只留下被消化后的知识。

## 一、为什么容易拼凑（失败机理）

写作时手里还摊着几篇原文，最省力的路径就是"这篇讲概念放第一节、那篇讲实操放第二节"——
章节边界 = 来源边界。三个症状：

- **章节按来源切**：这一节明显是 A 文档的缩写，下一节明显是 B 文档的缩写
- **来源提示语频繁出戏**："根据官方文档""有博主认为""另一篇文章提到"
- **断层**：A 讲完概念直接跳 B 的实操，中间的衔接（为什么这么做、前置知识）谁都没讲——
  因为那正是两篇文档共同的缺口

## 二、成文规则

1. **章节按主题自身逻辑组织**：是什么 → 为什么值得学 → 原理 → 装起来跑通 → 逐模块上手 →
   坑（骨架见 `assets/blog-template.md`）。每个知识块放在它逻辑上该在的位置，而不是它来源
   文档的位置
2. **一条叙事线**：全文像"我研究明白了讲给你听"，每节开头接住上一节尾巴；禁止出现"接下来
   看看另一篇文档怎么说"式的转场
3. **来源差异在写作期解决，不在文中罗列**：
   - 版本不同 → 按最新稳定版写，必要时括注（"v1 用法不同，见官方迁移指南"）
   - 场景不同 → 把各自的适用场景讲清楚，整合成一张对照
   - 裁不断 → 优先官方与最新；仍裁不断就并列陈述并标 uncertain
4. **正文零来源噪音**：不写"根据官方文档""有网友说"。个别 load-bearing 的事实需要强调
   时效 / 权威性时，用一句括注（"截至 2025-09，官方文档口径"），不做成结构
5. **来源的两个正当出口**：文末参考来源节（列表 + 各自贡献一句话）与图注署名。仅此两处

## 三、正反例

**反例（拼凑腔）**：

> 根据官方文档，X 是一个用于 Y 的工具。某技术博客指出，X 的性能比同类好 30%。另一位博主
> 分享了他的使用教程，首先安装……（各句各有所本，但像文献综述，不像文章）

**正例（消化腔）**：

> X 解决的问题是 Y——在它出现之前，大家只能 Z（笨办法）。它比同类工具快约 30%（官方基准，
> 场景有限定，见文末参考）。上手只要三步……

区别：正例里知识已经有了作者自己的组织（问题 → 笨办法 → 新方案 → 证据 → 行动），来源退到
幕后；数字仍在，但被放进了论证链，且标明了口径与限定。

**反例（断层）**：概念节讲完 X 的定义，下一节突然"在终端执行 `x init && x run`"——为什么
要 init、run 之后会发生什么，谁都没说。

**正例（接住）**：概念节末尾埋一句"理解了模型，下一步把它跑起来——先装环境"；实操节开头
一句"`init` 会生成默认配置，`run` 基于它启动服务，跑通后终端输出 …"。

## 四、动笔前与通读后的自检清单

动笔前：

- [ ] 大纲的每一节对应**知识块**而非某篇文档？
- [ ] 知识地图里的缺口都补上了（补查或明确标 uncertain）？

通读后：

- [ ] 遮住文末参考来源，全文是否自洽成立、读不出多源痕迹？
- [ ] 相邻两节是否出现"明显的换源感"（文风、口径、深度突变）？
- [ ] 术语口径全文一致（同一概念没换叫法）？
- [ ] 每个数字 / 关键事实都能追溯到参考来源中的某一篇？
- [ ] 删掉任何一篇来源，文章是否仍是完整的？（是 → 说明确实消化了；否 → 那篇还在"拼"着）
